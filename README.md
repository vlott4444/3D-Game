# Совет мудрецов

Браузерный многопользовательский 3D-зал для совместного решения задач. React, Three.js / React Three Fiber, Rapier, Colyseus, SQLite и локальная Ollama. Обновлено 1 ноября 2026 года.

## Запуск

Node.js 22.13+ и уже установленные зависимости. Новых пакетов для обновления диалога не требуется. На серверном компьютере должна работать Ollama с qwen2.5:3b; адрес и модель задаются OLLAMA_URL / OLLAMA_MODEL. Клиентам нужен браузер.

```bash
npm start
```

В другом терминале из корня проекта:

```bash
npm run dev --workspace=apps/frontend
```

Открыть http://localhost:3000. Для подключения другого ноутбука должны быть доступны порты 3000 и 2567 в локальной сети. Физический запуск на двух ноутбуках без интернета отдельно не проверялся.

## Взаимодействие

- WASD — движение, Shift — бег, пробел — прыжок, мышь — камера. Esc закрывает диалог / освобождает мышь.
- Рядом с отдельным мудрецом появляется E для разговора с ним. Рядом с круглым столом — E для обсуждения с советом.
- «Чат игроков» открывает канал людей из любой точки мира. Выпадающего списка адресатов больше нет.
- «В зал» возвращает к входу. От входа нужно подойти к столу или выбранному персонажу.
- Приблизиться к столу или NPC необходимо и по проверке сервера. Простого указания npcId в сообщении недостаточно.

Большое диалоговое окно занимает почти весь доступный экран. Основная переписка имеет собственную прокрутку, текст 17 px (16 px на узком экране). Задача, действия с посетителем, роли и состояния находятся сбоку. «О задаче» скрывает/открывает эту панель; «Развернуть» использует весь экран. На узком экране боковая информация открывается поверх чата только по запросу. Enter отправляет сообщение, Shift+Enter добавляет строку. Фокус остаётся внутри модального окна; Esc его закрывает.

## Задачи и посетители

Можно сразу обсуждать собственную задачу. У стола также можно пригласить одного посетителя с подготовленной проблемой. Он входит за пять секунд; после хотя бы одного ответа игрок решает, когда завершить приём. Посетитель уходит за пять секунд и удаляется из сцены. Автоматической проверки правильности решения нет.

В SQLite хранится каталог из 30 посетителей с именем, ролью, категорией и проблемой. При вызове выбирается случайная ситуация с учётом прошлых показов игрокам. Тексты ситуаций подготовлены заранее, ответы генерирует LLM. Отдельный разговор с самим посетителем пока не реализован. Текущий приём живёт в памяти комнаты и сбрасывается при перезапуске сервера.

Название и активный сценарий теперь «Совет мудрецов». Старый сюжет про убийство не используется в интерфейсе или запросах к модели. Старые данные в SQLite сохранены. В profiles оставлены только шесть актуальных файлов; четыре неактивных профиля убраны из проекта. История старого детективного режима не подмешивается в новый свободный разговор.

## Характеры и обмен доводами

Эйнштейн проверяет гипотезы, Найтингейл защищает необходимые потребности людей, Ада превращает идеи в правила, Макиавелли проверяет исполнение и интересы, Сократ уточняет критерии справедливости, Диоген ищет простое достаточное действие. Профили содержат приоритеты, методы, манеру речи и ситуационные подходы. Это художественные интерпретации личностей.

Обычному общему вопросу назначаются 1–3 участника. Имена в сообщении задают состав, «пусть ответят остальные» приглашает не отвечавших в прошлом ходе. Явно можно запросить полный круг. Диспетчер работает локальным алгоритмом по теме и давности выступления, не тратя отдельный LLM-вызов. Он всегда выбирает хотя бы одного человека.

Первый участник отвечает игроку. Следующий получает короткую настоящую цитату предыдущего предложения и задачу оценить её через свои приоритеты: возразить с основанием, уточнить риск или поддержать с условием/проверкой. Прежний разговор фиксируется на начало хода, а внутри хода передаётся отдельная цитата до 600 символов. Так есть конкретный предмет реакции без растущего пересказа всех ответов. В интерфейсе показано «В ответ: …» и начало обсуждаемого довода.

Спор не навязывается ради эффекта. Допускаются осмысленное согласие и воздержание следующих участников. Первый не может воздержаться; при недоступной модели выводится ошибка. Явные текстовые повторы отбрасываются; из частичного повтора сохраняется новая часть. Семантическая уникальность и логическая правильность каждого ответа не гарантированы маленькой моделью.

В комнате идёт один ход совета одновременно. Все профили обслуживает одна локальная модель, ответы последовательно ограничены 150 токенами. Canvas продвигает кадры вручную с бюджетом 40 Гц при игре / 12 Гц при диалоге. Это не гарантированный FPS на любом устройстве.

## Хранение и история

Регистрация/вход предшествуют WebSocket; сервер проверяет JWT. Новые пароли — scrypt, старые bcrypt-хеши поддерживаются. SQLite хранит состояние игроков и память. Поза передаётся примерно раз в 200 мс, записывается до подтверждения pose_saved; при входе восстанавливается последняя подтверждённая позиция. Не подтверждённое перед аварией движение может потеряться.

В таблице dialogue сохраняется память по игроку, персонажу и случаю; в LLM попадают последние восемь сообщений. Свободные задачи имеют отдельный case_id open-council; приёмы посетителей изолированы по UUID.

Для интерфейса добавлены chat_entries и chat_receipts: один вопрос записывается один раз, а не по числу ответивших NPC. Сохраняются канал, случай, адресат реакции и список получателей комнаты. История выдаётся только получателю, отдельно для совета, каждого NPC и чата игроков. Реплики видны игрокам той же комнаты; это не приватная переписка. В интерфейс загружается до 100 последних записей канала и случая, суммарный клиентский буфер ограничен 300 сообщениями. Активный приём после перезапуска не восстанавливается, хотя его записи остаются в БД.

Старые таблицы и записи не удаляются. Миграция создаёт недостающие таблицы истории, каталог посетителей и сохранения изменений мира. Существующие аккаунты, позиции и секрет авторизации сохраняются.

## Мир и пределы реализации

Сервер создаёт детерминированные чанки 64×64 по seed и координатам. Клиент получает окно 3×3 через авторизованный WebSocket и заменяет старые чанки новыми. Не более девяти чанков и 90 процедурных объектов активного окна. Деревья и камни используют instancedMesh. Зал и шесть мудрецов — постоянная сцена фиксированного размера.

Координаты продолжаются за прежней границей; технический предел — 10 миллионов по модулю. Для очень дальнего мира нужен floating origin. Лимит девяти чанков ещё не доказывает требование ТЗ «≤10% всех данных мира»: нужны конечный манифест, учёт ресурсов в байтах и проверка отношения cachedBytes/totalWorldBytes. WebXR, голос, голосование за доводы и коллаборативные рекомендации пока не реализованы.

## Проверки

42 автоматических теста: сохранения, JWT/пароли, авторизация WebSocket, два клиента, выбор участников, настоящая передача цитаты в запрос следующему агенту, память, каналы/получатели истории, перезапуск SQLite, расстояния до стола/NPC, посетители, чанки. TypeScript backend/frontend и production-сборки проходят. Предупреждение Vite о пакете около 3,6 МБ остаётся.

Браузерный тест с контролируемой моделью прошёл подход к столу/Диогену, E, отсутствие select, общий и отдельный каналы, карточки реакций, чат игроков, Esc и разворот окна. Проверены размеры 1440×900, 1280×720, 800×650, 390×740. Высота переписки соответственно около 585, 405, 345, 460 px; ошибок JavaScript нет.

Отдельно проверена настоящая qwen2.5:3b: Макиавелли предложил проверяемое расписание, Сократ отреагировал с обращением «Возражу, Макиавелли» и спросил, кто проверит выбранного мастера. Запросы заняли примерно 23 и 27 секунд без дополнительной 3D-сцены. Это результат конкретной проверки, не обещание скорости или качества каждого ответа.

Проверки выполнены на Windows Node.js 24 в отдельной копии проекта; установщик повторяет проверки в WSL. Прямой командный доступ к WSL в текущей сессии возвращает Wsl/E_ACCESSDENIED, поэтому изменения применяются через apply-dialogue.sh.

## Каталог посетителей и защита от повторов

По умолчанию используется apps/backend/data/game.db; при заданном DB_PATH — указанный файл. Источник первичного наполнения — src/agents/visitors/catalog.json. Первый запуск добавляет 30 строк в visitor_catalog, существующие строки не перезаписываются. enabled=0 исключает ситуацию из выбора. Правки уже заведённой ситуации следует делать в БД; новый id в catalog.json добавляется при следующем запуске. player-сохранения при наполнении не меняются.

visitor_seen хранит число показов и последний показ для каждого игрока, visitor_draws — журнал вызовов, visitor_presence — участников конкретного приёма. Учитываются все подключённые игроки комнаты, включая поздно вошедших; повторный вход во время того же приёма не увеличивает счётчик повторно.

Выбор случайный среди наименее показанных допустимых ситуаций. Для одного игрока сначала проходит весь каталог из 30 записей. Последние восемь случаев временно исключаются, в том числе на границе циклов. В группе с разными историями окно постепенно уменьшается только если иначе нет кандидатов; при стандартных 30 случаях и максимум восьми игроках остаётся возможность исключить как минимум последние три случая каждого. Если вручную оставить очень маленький каталог, столь длинное окно соблюдать невозможно. История выбора переживает перезапуск сервера. Активный незавершённый приём пока не восстанавливается.

## Многочисленные обычные NPC

Это отдельный класс без LLM: по 18 существ на чанк, максимум 162 в активном окне одного клиента — 108 жителей и 54 оленя. Сервер симулирует только объединение окон около игроков и удаляет старые участки. Клиент заменяет набор, не накапливая всех посещённых NPC.

- Жители гуляют; останавливаются и поворачиваются на разговор или жест поблизости.
- При приближении бегущего игрока жители уступают, олени отбегают.
- G / «Позвать» привлекает внимание ближайших жителей.
- F / «Угощение» оставляет временную порцию снаружи зала; ближайшие олени подходят и останавливаются около неё.
- Угощение исчезает через 6,5 секунды. Без новых стимулов существа возвращаются к прогулке.

Поведение реализовано конечными состояниями wander/look/yield/flee/eat на сервере, с проверкой расстояния и времени. Обновление симуляции — 10 Гц, отправка состояний подписанным клиентам — 5 Гц. Два клиента одной комнаты получают одно серверное состояние общих NPC. Графика использует 15 instancedMesh для всех частей тел; мелкие части скрываются на расстоянии, индивидуальные тени толпы отключены. Фоновые NPC не имеют отдельных физических тел и не заменяют полноценный navmesh/симуляцию транспорта. Избегание зала, стволов и площадок построек упрощённое. Транспорт в проекте не добавлялся; уступают именно бегущему игроку.

## Мудрецы изменяют окружение

Попроси выбранного мудреца или совет: «Ада, создай доску идей», «Поставь скамейки», «Создай питьевой пункт», «Посади сад». В боковой панели есть кнопки, подставляющие эти просьбы в поле; отправка остаётся действием игрока. Поддерживаются также «Переставь скамейки» и «Убери сад». Одно сообщение — один тип объекта. При общем вопросе действие получает первый выбранный участник совета.

Локальный классификатор принимает только прямую команду из набора действий/объектов. «Не создавай сад», цитата или «что если поставить скамейки?» не изменяют мир. Сообщение в канале игроков ничего не строит. Клиент не задаёт произвольные координаты: сервер размещает объекты на подготовленных площадках перед залом.

На каждый из четырёх типов есть одно место: доска, пара скамеек, питьевой пункт и сад. Повторное создание не добавляет дубликаты. Перенос переключает безопасные варианты расположения; удаление убирает объект. world_edits хранит текущий состав, world_meta — ревизию, world_edit_log — журнал действий с игроком и агентом. Изменения сохраняются в SQLite, видны другим клиентам и поздно подключившимся игрокам, восстанавливаются после перезапуска. Изменения передаются только в соответствующих активных чанках.

Это не генерация произвольных 3D-моделей нейросетью: локальный классификатор управляет четырьмя подготовленными типами. Изменение применяется сразу, а служебная реплика «Окружение · имя агента» сообщает результат. Обычный ответ LLM идёт отдельно и получает подтверждённый результат сервера. Поэтому физическое изменение не зависит от фантазии модели; при сбое LLM уже применённый объект остаётся.

Площадка перед входом освобождена от процедурных деревьев, чтобы можно было пользоваться новым двором. Основное окно диалога, подходы к мудрецам/столу и история переписки сохранены.

## Очередь ИИ и проверка обновления

Мудрецы не генерируют ответы одновременно. Один запрос LLM завершается, публикуется ответ; затем запускается следующий, уже с цитатой предыдущего. Одна очередь AgentService обслуживает одну локальную модель. Массовые NPC, выбор посетителя и создание объектов LLM не используют.

42 теста проходят: в том числе циклы случайного каталога, перезапуск SQLite, смешанные истории восьми игроков, отсутствие лишних профилей/старого сюжета, реакции толпы, выгрузка старых участков, отсутствие LLM-вызовов от обычных NPC, общие состояния двух клиентов, создание объекта агентом, поздний вход, сохранение/перенос/удаление и пространственная фильтрация построек. Проверки TypeScript и обе сборки проходят.

В настоящем браузере с контролируемыми ответами LLM проверены создание четырёх объектов через диалог, видимые модели, жест, угощение, прогулка по двору и счётчики 9/9 чанков / 162 NPC; ошибок JavaScript нет. Это функциональная проверка, а не замер производительности на Intel GPU и не гарантия FPS. Физическая LAN-сессия на нескольких ноутбуках отдельно не испытывалась.

Новых зависимостей нет. Для применения используется apply-living.sh: резервное сохранение исходников и данных, перенос четырёх устаревших JSON в резервную папку, проверка источников, тесты и сборки. Скрипт не заменяет game.db, .env или индекс Git. Ограничение «≤10% данных всего мира» по-прежнему не доказано одним лимитом девяти чанков — для него нужен согласованный конечный манифест и учёт байтов ресурсов.


## Объединение с vit и feature/frontend

Полупрозрачный чат игроков, уведомления входа/выхода и пагинация общей переписки объединены с большим диалогом, пространственным E, портретами и нашей живой сценой. Личные разговоры теперь отправляются только владельцу аккаунта; память LLM разделена на private/council. Публичная переписка синхронизируется между комнатами одного процесса сервера.

Админка показывает FPS сцены/пинг и сохраняет дополнительную инструкцию выбранного мудреца в agent_overrides. API требует JWT и роль администратора. По умолчанию роль получает самый ранний зарегистрированный аккаунт; ADMIN_USERNAME задаёт явного владельца. Инструкции действительно добавляются к запросу LLM, при сбросе восстанавливается JSON-профиль. Подробнее — CHAT_UPDATES.md.


## Лесной городок и интерактивные предметы

Восемь небольших зданий с открываемыми дверями, дорожки и площадь расположены вокруг главного зала. HUD компактен; админка — немодальная сворачиваемая панель. R — предмет/дверь, Q — положить, T — бросить, N у жителя — проводник к совету.

Пять мячей и пять ящиков имеют общую серверную физику: гравитация, отскоки, трение и столкновения. interactive_objects хранит последнее сохранённое положение вещей и двери. Один предмет может держать только один игрок; при выходе он освобождается. Перемещения игроков, AI-профили и прежние диалоги не сбрасываются. Городок приходит внутри world_snapshot, предметы — через object_snapshot, только для текущей окрестности. Нет новых npm-зависимостей.

50 тестов и проверки типов/сборок проходят. Навигация жителей и физика предметов упрощены. Сохранение положения брошенного предмета не означает непрерывное сохранение всей траектории. В браузере проверены ходьба с открытой админкой, предметы и двери. Это не замер аппаратной производительности.
